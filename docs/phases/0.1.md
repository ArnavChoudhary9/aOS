# 0.1 — Workspace, xtask, Limine ISO

**Spec:** [phase-0.1-workspace-xtask-limine.md](../roadmap/phase-0.1-workspace-xtask-limine.md)

## What was built

- **A Cargo workspace** with two members:
  - `kernel`, built for `x86_64-unknown-none`;
  - `xtask`, a host tool.
  - A plain `cargo build` at the root only builds `xtask`. Target crates are always built through `cargo xtask`.
- **A pinned toolchain**: stable Rust 1.98.1 with the bare-metal target, rustfmt, clippy and llvm-tools.
- **`cargo xtask build | image | run`**:
  - `build` compiles the kernel.
  - `image` downloads a pinned Limine release once, checks its SHA-256, and packs a BIOS-bootable ISO.
  - `run` boots that ISO in QEMU (KVM by default, `--tcg` for interrupt logging, `--gdb` for a GDB stub).
- **A relocatable (PIE) kernel.** Limine loads it at a different random address on every boot (KASLR). The kernel prints that address on COM1 and halts:

  ```text
  aOS kernel 0.1.0 base=0xffffffffe8485000 phys=0x1fe2c000
  limine: rev=3 hhdm=yes memmap=yes modules=no framebuffer=yes rsdp=yes cmdline=""
  ```

## How Limine loads a PIE kernel, and where KASLR comes from

1. Rust's `x86_64-unknown-none` target, with `-C relocation-model=pie`, produces a **static-PIE**:
   - an ELF of type `ET_DYN`;
   - a `PT_DYNAMIC` segment;
   - a table of `R_X86_64_RELATIVE` relocations. Each one says "the 8 bytes at address A must hold link-address B plus the load offset".
2. The linker script links the kernel at `0xffffffff80000000` (the top 2 GiB) and keeps `.rela.dyn` inside a loadable segment, so Limine can read the table.
3. Limine sees `ET_DYN` plus `PT_DYNAMIC` and treats the kernel as relocatable. Because `limine.conf` has `kaslr: yes`, it picks a random **slide**:
   - a multiple of the largest segment alignment (4 KiB here);
   - small enough that the kernel stays in the top 2 GiB.
4. Limine copies each segment to `link address + slide` and walks the relocation table, adding the slide wherever needed.
5. The executable-address response tells the kernel where it ended up: `virtual_base = 0xffffffff80000000 + slide`.

Run it a few times and the `base=` value changes each time. `phys=` usually stays the same, because KASLR randomizes the *virtual* address, not where in RAM the kernel sits. Limine also randomizes the higher-half direct map (HHDM) base by default when KASLR is on.

A useful check: `readelf -r target/x86_64-unknown-none/debug/kernel` shows about 73 relocations, all `R_X86_64_RELATIVE`. Any other kind would mean code that needs a dynamic linker.

## What each Limine request is for

The requests are statics between a start marker and an end marker in their own section. Limine scans the image for them before jumping to `kmain`, and fills in each response pointer.

| Request | Used | For |
| --- | --- | --- |
| `BaseRevision(3)` | now | Which protocol revision we speak. `is_supported()` is checked first |
| `ExecutableAddress` | now | Physical and virtual base: the KASLR proof |
| `ExecutableCmdline` | logged | Kernel command line (`aslr=off`, `log=`; from 1.7) |
| `Hhdm` | logged | Offset of the direct map of physical memory (1.1) |
| `MemoryMap` | logged | Usable RAM and reserved regions (1.1) |
| `Module` | logged | rootsrv and boot.tar (1.7, 3.1). "no" for now, since none are configured |
| `Framebuffer` | logged | Screen for fbcon/compositor (10.x) |
| `Rsdp` | logged | ACPI tables for APIC setup (1.4) |

## ISO layout

```text
/boot/kernel.elf
/boot/limine.conf
/boot/limine/limine-bios.sys       Limine stage 3 (BIOS)
/boot/limine/limine-bios-cd.bin    El Torito boot image
```

QEMU boots it with `-cdrom`. The BIOS loads `limine-bios-cd.bin` through El Torito (`xorriso -b`). That loads `limine-bios.sys`, which reads `/boot/limine.conf` and loads the kernel.

## Key decisions (also in the design doc's Decision log)

- **`limine` crate pinned to 0.5.0, base revision 3.** Version 0.6.x uses `#![feature(ptr_metadata)]`, which needs nightly and breaks the stable-only decision. Limine v12 still accepts revision 3 on x86_64 (only aarch64 requires 6). Revision 6 needs either a newer crate that builds on stable or our own request bindings.
- **Limine v12.9.6.** It is the newest release that has been out more than two weeks; v12.11.1 was 6 days old.
- **No `limine bios-install` on the ISO.** The spec said to run it, but it only adds hybrid USB/HDD boot. It fails on a BIOS-only ISO, which has no partition at sector 63 or later. Booting via `-cdrom` doesn't need it. It comes back in 11.3, when aOS boots from a partitioned disk image.
- **xtask has no dependencies.** It calls `curl`, `tar`, `sha256sum`, `make`, `xorriso` and `qemu-system-x86_64`, and fails with an install hint if one is missing.
- **Frame pointers and PIE are set for the target** in `.cargo/config.toml`, so every later bare-metal crate inherits them.

## Try breaking it

1. **Remove `kaslr: yes`** from [boot/limine.conf](../../boot/limine.conf) and boot twice. `base=` is now always `0xffffffff80000000`, the link address.
2. **Make the kernel non-relocatable.** Change `relocation-model=pie` to `static` in `.cargo/config.toml` and rebuild. `readelf -h` now says `EXEC`, and `base=` stops changing even with `kaslr: yes`, because Limine only slides `ET_DYN` images. Revert afterwards.
3. **Corrupt the checksum.** Change one hex digit of `SHA256` in [xtask/src/limine.rs](../../xtask/src/limine.rs), delete `target/limine`, then run `cargo xtask image`. It fails with `Limine checksum mismatch` and does not use the download. Revert afterwards.
4. **Watch the boot under TCG.** Run `cargo xtask run --tcg`, then open `target/qemu-int.log`. You can see BIOS and Limine interrupts. There should be no `cpu_reset` lines; a triple fault would show up as one.
