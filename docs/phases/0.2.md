# 0.2 — Gate harness

**Spec:** [phase-0.2-gate-harness.md](../roadmap/phase-0.2-gate-harness.md)

## What was built

- **`cargo xtask gate <name>...` and `cargo xtask gate --all`.** Each run boots aOS in QEMU under a spec in `tests/gates/<name>.toml` and checks two things:
  - the expected log lines appear, in order;
  - the guest reports success through QEMU's `isa-debug-exit` device.

  This is the automated check every later phase must pass, and `--all` makes sure earlier phases haven't regressed.
- **`cargo xtask check`** runs four steps and fails if any fails:
  - `cargo fmt --check`;
  - clippy with `-D warnings` for host crates;
  - clippy with `-D warnings` for bare-metal crates;
  - host unit tests.
- **Kernel side:**
  - `qemu::exit(Success | Failure)` writes the status to port 0xF4.
  - The kernel exits with `Success` when its cmdline contains the word `gate`, which the harness always adds.
  - The panic handler now exits with `Failure`, so a panic fails a gate immediately instead of timing out.
- **The first gate, `tests/gates/smoke.toml`.** It checks the phase 0.1 boot line, with the KASLR base in the upper 2 GiB, plus the Limine summary line showing `cmdline="gate"`.

```text
$ cargo xtask gate smoke
[com1] aOS kernel 0.1.0 base=0xffffffffe8a55000 phys=0x1fe1d000
[com1] limine: rev=3 hhdm=yes memmap=yes modules=no framebuffer=yes rsdp=yes cmdline="gate"
gate smoke: PASS (0.6s)
```

## The spec format

```toml
name    = "smoke"     # must equal the file name (tests/gates/smoke.toml)
cmdline = "log=debug" # extra kernel cmdline; `gate` is always prepended
stream  = "com1"      # com1 (QEMU stdio) or com2 (log file, the default from 0.3 on)
timeout = "20s"       # whole run: 500ms, 20s, 2m (default 30s)

[kernel]
features = ["test-panic"]   # kernel cargo features for this boot

[[expect]]                  # regexes, matched in order
re = '^aOS kernel \d+\.\d+\.\d+ base=0xffffffff[0-9a-f]{8}'
```

The rules:
- Unknown fields are errors (`deny_unknown_fields`), so `timout = "5s"` fails loudly instead of being ignored.
- Each expectation must match a line *after* the one that matched the previous expectation.
- One line may satisfy several consecutive expectations.
- Fields for later phases (`stdin`, `services`, `disk`, `post`, `expect_exit`, …) are added by the phases that first need them.

## How exit codes map

QEMU's `isa-debug-exit` makes QEMU exit with `(value << 1) | 1`.

| Guest writes | QEMU status | Harness says |
| --- | --- | --- |
| `0x10` (`QemuExit::Success`) | 33 | success. Required for PASS |
| `0x11` (`QemuExit::Failure`) | 35 | "the kernel reported failure" |
| nothing, QEMU still running at the timeout | killed | "timeout" |
| anything else, e.g. a triple fault with `-no-reboot` | other | "did the kernel call qemu_exit?" |

A gate passes only if **every expectation matched and the status is 33**. Matching every line but then hanging is a failure, and so is exiting 33 without matching everything.

## How a run works

1. Parse and validate the spec.
2. Build the kernel with the spec's features and copy it into `target/gates/<name>/`.
3. Write a `limine.conf` whose `cmdline:` is `gate <spec cmdline>`, then pack a per-gate ISO in that directory.
4. Start QEMU with the standard machine plus `isa-debug-exit`. COM1 goes to a pipe and COM2 to `com2.log`.
5. Two reader threads feed lines into one channel:
   - a COM1 reader saves `com1.log` and echoes each line as `[com1] …`;
   - a COM2 tailer follows the growing log file.
6. The main loop feeds lines from the spec's stream to the matcher until QEMU exits or the timeout passes, killing QEMU in the second case.
7. Drain any lines still in flight, then decide. A failure prints:
   - the unmatched regex;
   - the exit reason;
   - the last 40 lines of the stream;
   - QEMU's stderr;
   - the log directory.

## Key decisions

- **Logs are always kept** in `target/gates/<name>/`: kernel, ISO, `com1.log`, `com2.log`, `qemu-stderr.log`. The spec mentioned a `--keep` flag, but keeping logs costs nothing and is what you want after a failure. They're replaced on the next run of that gate.
- **No ISO cache.** The spec suggested caching per-gate ISOs by content hash. Packing takes well under a second, so a cache isn't worth the complexity yet.
- **Gates run under KVM by default.** `gate --tcg` uses software emulation, for machines without `/dev/kvm`.
- **xtask's first dependencies:** `serde` 1.0.229, `toml` 0.9.8 and `regex` 1.13.1, each pinned exactly. regex 1.13.2 was skipped because it was only 9 days old.
- **The panic handler exits with `Failure` now** rather than in 0.3, because without it a panicking gate waits out its whole timeout.

## Adding a gate for a new phase

1. Create `tests/gates/<id-or-name>.toml` with `name` equal to the file name.
2. If the test needs special kernel code, add a cargo feature to `kernel/Cargo.toml` (for example `test-panic = []`) and list it under `[kernel] features`.
3. Make the kernel print stable, greppable lines (see the log format in the roadmap README) and call `qemu::exit(Success)` at the end of the scenario.
4. Run `cargo xtask gate <name>`, then `cargo xtask gate --all`.

## Try breaking it

1. **A wrong expectation.** Add `[[expect]] re = 'nonsense'` to a copy of `smoke.toml` (rename both the file and its `name`). The run fails with `unmatched: expect #3 of 3 … /nonsense/` and the log tail, even though QEMU exited 33.
2. **Forget to exit.** Comment out `qemu::exit(QemuExit::Success)` in `kernel/src/main.rs`. The gate fails with `killed (timeout)` after its timeout, instead of hanging forever.
3. **Panic.** Put `panic!("test")` before that line. The gate fails in under a second with `QEMU exit: 35 (the kernel reported failure)`, and the panic message appears in the tail.
4. **A typo in a field.** Rename `timeout` to `timout` in the spec. You get a parse error naming the unknown field before QEMU even starts.
