# 0.3 — Kernel logging, panic, backtrace

**Spec:** [phase-0.3-logging-panic-backtrace.md](../roadmap/phase-0.3-logging-panic-backtrace.md)

## What was built

- **Two serial ports with distinct jobs.**
  - **COM1** is `-serial stdio`, your terminal. It shows console lines and anything at `WARN` or above.
  - **COM2** goes to a file: `target/aos-log.txt` for `cargo xtask run`, or `target/gates/<name>/com2.log` for a gate. It is the full log, and gates parse it.
- **Logging macros**: `kerror!`, `kwarn!`, `kinfo!`, `kdebug!` and `kprintln!`. Every line uses the format gates match on:

  ```text
  [    11] INFO  kernel: slide=0x5b2ff000
  ```

  `log=debug` (or `error`, `warn`, `info`) on the kernel cmdline sets the COM2 level.
- **A real panic handler.** It prints the message and location, walks the stack through frame pointers, prints each return address, and exits QEMU with the failure status. It is safe against panics while panicking and against panics while holding a UART lock.
- **`cargo xtask symbolize [LOG] [--elf PATH]`.** It finds the `slide=` line in a log, subtracts it from every `bt:` address, and resolves them with GNU `addr2line`. Gates do this automatically whenever a log contains a backtrace.
- **`cargo xtask gdb`.** It attaches GDB to `cargo xtask run --gdb`, which now boots with KASLR off and paused, and puts a hardware breakpoint on `kernel_main`. If you attach to a KASLR boot instead (`cargo xtask run -- -s`), it reads the slide from `target/aos-log.txt` and loads symbols at that offset.
- **Gate harness additions:**
  - `expect_exit = "failure"`, for gates that are meant to panic;
  - `[[reject]]` patterns: any matching line fails the gate;
  - three new gates: `panic`, `console` and `loglevel`.

## How frame-pointer unwinding works

Every target crate is built with `-C force-frame-pointers=yes`, so every function begins with:

```asm
push rbp        ; save the caller's frame pointer
mov  rbp, rsp   ; rbp now points at that saved value
```

That turns the stack into a linked list:

```text
 higher addresses
 ┌─────────────────────┐
 │ return address      │  [rbp_caller + 8]
 │ saved rbp ──────────┼──► ...
 ├─────────────────────┤ ◄── rbp_caller
 │ ...callee locals... │
 │ return address      │  [rbp + 8]   → somewhere in the caller
 │ saved rbp ──────────┼──► rbp_caller
 └─────────────────────┘ ◄── rbp (current frame)
 lower addresses
```

[`backtrace::walk`](../../kernel/src/arch/x86_64/backtrace.rs#L34) starts at the current RBP. For each frame it reads `[rbp + 8]` as the return address and `[rbp]` as the next RBP. It stops at the first frame that fails a sanity check:
- the frame pointer is null, misaligned, or outside the higher half;
- the frame pointer isn't above the previous one, or is more than 1 MiB above the first;
- the return address points outside kernel `.text`, bounded by the new linker symbols `__text_start` and `__text_end`;
- 32 frames have been reported.

Bad frames mean garbage, and reading garbage pointers inside a panic handler would make things worse.

**Why "minus 1"?** A return address points at the instruction *after* the `call`. That instruction may belong to the next source line, or even to a different inlined function. Reporting `ret - 1` lands inside the `call` instruction itself, so the symbolizer names the line that made the call.

## How the KASLR slide is removed

At boot the kernel logs `slide=0x…`, which is Limine's chosen virtual base minus the link base `0xffffffff80000000`. Backtrace addresses are runtime addresses, but the DWARF in the ELF describes link-time addresses. `xtask symbolize` therefore:
1. finds the *last* `slide=` line, so a log holding several boots uses the newest;
2. keeps only `bt:` lines after it;
3. runs `addr2line -f -C -i -a -e <kernel ELF> <addr - slide>...`.

The `-i` flag prints inlined frames too, shown as `inlined in …` lines. The ELF must be the exact build that produced the log, which is why gates keep `target/gates/<name>/kernel.elf`.

## Key decisions (in the Decision log)

- **GNU `addr2line` (binutils) instead of the `addr2line` + `object` crates.** rustup's `llvm-tools` component doesn't ship `llvm-addr2line`. binutils is on virtually every Linux dev machine and handles Rust demangling and DWARF 5. This keeps xtask's dependency tree small.
- **`kprintln!` is a console line.** It is printed as-is on COM1 and logged at INFO on COM2. That keeps the boot banner visible in your terminal while INFO noise stays in the log file. The `console` gate's `[[reject]]` rule checks that INFO lines never reach COM1.
- **`run --gdb` turns KASLR off**, so the ELF's symbols are correct from the first instruction. Attaching to a randomized boot is still supported through the logged slide.
- **Hardware breakpoint for `kernel_main`.** At reset the kernel isn't mapped, so GDB can't plant an `int3`. An `hbreak` uses the CPU's debug registers, which match on the virtual address once the kernel is running.
- **Timestamps are approximate until 1.4.** The TSC frequency comes from cpuid leaf 0x15 or 0x16 when the CPU reports them; otherwise it's a 1 GHz guess. KVM on this host reports neither. The boot log line says which source was used.
- **Panic-path locking.** `log::emergency` uses `try_lock`. If a UART is already locked, because the panic happened mid-log, it writes to the port anyway rather than deadlocking. A second panic prints `double panic` and exits.

## Try breaking it

1. **Turn off frame pointers.** Remove `force-frame-pointers=yes` from `.cargo/config.toml` and run `cargo xtask gate panic`. The backtrace shrinks to one or two frames, or turns to garbage, because RBP is now an ordinary register. Revert afterwards.
2. **Skip the slide.** Run `cargo xtask symbolize target/gates/panic/com2.log` with *no* `--elf` after a plain `cargo xtask build`. Function names may still resolve, but against the wrong build. Then delete the `slide=` line from a copy of the log and symbolize it: you get an error, not wrong answers.
3. **Panic while holding the log lock.** Add `let _g = COM2.lock(); panic!()` inside `log::log`. The panic output still appears, through `emergency`'s unlocked fallback, instead of hanging.
4. **Step through the boot.** Run `cargo xtask run --gdb` in one terminal and `cargo xtask gdb` in another, then `continue`, `next`, `next`… and watch the lines land in `target/aos-log.txt` (`tail -f`).
